Case study · Frame 04.2

Teaching a model a new object in seconds.

A few-shot learning pipeline added to an AI object counter, so a user can name a class the model has never seen, upload a handful of examples in the browser, and have the counting pipeline recognise it straight away.

ContextM.Sc. AI Engineering Lab
Base modelResNet-50
MethodTransfer learning
Taught from5 to 10 images

The problem

The object counter worked, but its knowledge was fixed at build time. It could only count things that were already in its class list, which meant the answer to most real requests was no. Someone who wanted to count a specific product, a coffee mug say, was out of luck unless a coffee mug happened to be one of the original categories.

The obvious fix, retraining the network on an expanded class set, is the wrong shape for the problem. It needs a large labelled dataset the user does not have, and hours of compute for a request that should feel instant. It also puts a machine learning engineer in the middle of every new class, which defeats the point of shipping the tool to anyone else.

So the question became: can the user teach the model themselves, from a handful of images, without retraining the network and without waiting?

The approach

The whole design rests on one observation: a pretrained ResNet-50 already knows how to see. What it does not know is the name of your object. Those are different problems, and only the second one needs new training. ResNet-50 was chosen for its balance of accuracy against resource cost, which matters when training runs on demand rather than overnight.

1. Freeze what already works

Every convolutional layer has requires_grad set to False before anything else happens. The general visual features learned from ImageNet are exactly what makes learning from five images possible at all, and leaving them trainable on a tiny user-supplied set is how you get catastrophic forgetting: the model trades everything it knew for the one thing you just showed it.

2. Grow the classifier head by one neuron

ResNet-50 ends in a classifier sized for ImageNet's 1,000 classes. The implementation reads the input feature size off that final linear layer, builds a new one with exactly one more output neuron, then copies the original weights and biases across before swapping it in. The copy is the important part. Without it, adding a class would silently reset every class that came before.

3. Prepare the user's images the way the model expects

A custom PyTorch dataset loads the uploaded files, resizes them to 224 by 224, and normalises with the same mean and standard deviation used in the original pretraining. This is unglamorous and it is also where this kind of feature usually breaks: feed a pretrained backbone differently normalised pixels and it will quietly underperform rather than fail loudly.

4. Train only the head

A short loop, roughly ten epochs, driven by a DataLoader with AdamW and cross-entropy loss. Only the new head's parameters carry gradients. Because the frozen backbone does all the heavy lifting and the trainable surface is a single layer, the model learns a new concept in seconds rather than the hours a full retrain would cost.

Making it a feature rather than a script

A fine-tuning function is not a product. Most of the work was turning it into something a person could use without being told how it worked, which meant restructuring the backend and rebuilding the interface around the training loop.

Backend, split by responsibility

  • ai_models.py loads the core models into memory once at startup.
  • few_shot_trainer.py holds all the PyTorch fine-tuning logic.
  • ai_pipeline.py was refactored down to inference only.

Two endpoints connect the frontend to it: POST /api/train takes the new class name and its images and runs the training, and GET /api/labels returns the current class list so the interface always reflects what the model actually knows.

Keeping the interface honest about the model's state

A CUSTOM_LABELS set tracks classes added at runtime, and the labels endpoint serves the union of that set and the base labels. It is a small mechanism, but it is what stops the dropdown and the model from drifting apart, which is the usual failure mode for features that mutate a model while the app is running. User-supplied training images are written to a training_data/ directory organised by class name, so there is a record of what the model was taught and a starting point for retraining later.

A teaching loop that closes

The interface got a dedicated Teach AI tab, deliberately separated from ordinary counting so the advanced path does not clutter the simple one. It walks through three steps, naming the object, uploading examples with visual previews, and starting the training, with a spinner and status messages while the model trains. When it finishes, the dropdown in the counting tab updates immediately with the new class. That last detail is the one that makes the feature feel real: the user's action visibly changes what the tool can do, straight away, with no reload and no explanation needed.

How do you evaluate a class that did not exist an hour ago?

This is the genuinely awkward part, and worth stating plainly rather than hiding behind a number. There is no held-out labelled test set for a category a user invented five minutes ago, so conventional test metrics are not available at training time.

Qualitatively, the loop works: given five to ten clear examples of a new object, a stapler in testing, the counting pipeline identifies and counts it in images it has not seen, and the zero-shot classifier at the end of the pipeline maps the newly fine-tuned classification onto the correct final label. The adaptation propagates through the whole pipeline, not just the layer that was trained.

Quantitatively, the answer was to move measurement out of training and into production. A Grafana dashboard reads a user correction mechanism, which turns everyday usage into labels and makes the standard classification metrics computable on real traffic:

MetricQuestion it answersWhy it matters here
AccuracyWhat share of counts were correct?Useful headline, but misleading when images hold few objects
PrecisionOf the objects claimed, how many were real?Catches over-counting and false alarms
RecallOf the objects present, how many were found?Catches under-counting and misses
F1Balance of the twoSingle number for comparing pipeline versions

The part I find most useful is the pipeline version filter. Because metrics are tagged by version, the dashboard can compare the model before and after a new class was taught. A drop on the original classes after training is the visible signature of catastrophic forgetting, so the design decision from step one has an ongoing test rather than just an argument behind it.

What this design costs

  • Garbage in, garbage out, and the user holds the bag. Performance on a new class depends entirely on the quality, quantity and consistency of the images someone uploads. Blurry, occluded, or unrepresentative examples produce a confidently wrong class, and the person best placed to cause that problem is the same person least equipped to diagnose it.
  • Training is stateful and in memory. The fine-tuned model exists in the running server's memory and is never written to disk. Restart the application and every taught class is gone. This is the single largest gap between this and something deployable, and the fix is known: persist the state dict and load it on startup.
  • One neuron per class does not scale. Widening the final layer works cleanly for a handful of custom objects. At hundreds it bloats the model and forces a retrain of the head against all custom data each time. A scalable version would compare embeddings instead, something like CLIP matching image embeddings against text embeddings, which adds classes without changing the architecture.
  • New classes are structurally more fragile than old ones. Original classes were learned from ImageNet's diversity. A taught class rests on one person's small and possibly biased sample. Freezing the backbone limits the blast radius, but degradation on visually similar original classes is still possible, which is precisely why the monitoring comparison exists.

What I would do next

Two changes would move this from a working prototype toward something I would be willing to run for other people. Persisting the fine-tuned weights after training and reloading them at startup is the immediate one, and it is small. Replacing the grow-the-head approach with an embedding similarity architecture is the larger one, and it is what would let the tool hold hundreds of user-defined classes instead of a handful.

The broader lesson I took from it: the machine learning here is roughly forty lines. Everything that made it usable, the module boundaries, the label synchronisation, the correction loop feeding monitoring, and the three-step interface that closes visibly, was the other ninety percent of the work.
